### From Dev Director's Notes:

**Core Vision & Intent:** WordRun is a mobile word-association puzzle game merging word-chain mechanics with Candy Crush-style progression across 3,000 levels organized into 120 "lands." Built with Phaser 3, Vite, TypeScript, and Supabase, targeting mobile portrait (390×844) with aggressive performance targets: 60 FPS on mid-range devices, <2MB initial bundle, <150MB RAM.

The story is infused directly into gameplay, not an add-on. Advancing in the game means understanding its lore. Narrative delivery through NPC speech cards between levels, context-sensitive dialogue during gameplay, and word choices/mechanics that evolve with narrative progression.

2. **Story & Lore Integration:** In Progress - 9 nations defined, 8-beat story structure, travel routes, complete language design system
3. **Monetization Strategy:** Pending - Ethical framework established (never gates story/progression)
4. **Design Excellence:** In Progress - Emotional design research complete (58K words), UI analysis pipeline complete (3 testable configurations)

**Visual Appeal & UX Goals:** Native app feel on par with Candy Crush and Wordscapes. Emotional core: Accomplishment + Curiosity + Calm Confidence + Delight. Typing microinteraction is CRITICAL (<100ms start, 300-500ms complete). Ruut character requires 3-4 varied celebration animations. Story integration: 3-5 sec NPC dialogues (skippable), 30-60 sec cutscenes (replayable).

### Ideas Explored but Ultimately Rejected:

#### 1. Orthogonal Grid System (Agent B Options B & C)

**Explored:** Agent B provided three grid mockup options:
- Option A: True Isometric Grid (60° diamond projection)
- Option B: Faux Isometric (rectangular grid with isometric-styled tiles)
- Option C: Pure Orthogonal Grid (top-down, no perspective)

**Rejected:** Options B and C (User selected Option A)

**Rationale:** True isometric provides authentic depth perception, matches visual inspiration images, supports visual storytelling (nation-specific terrain).

#### 2. Gemini-Only Extraction Pipeline (No Python Fallback)

**Explored:** Original plan used Gemini for all extraction and interpolation stages.

**Rejected:** Due to rate limits, had to add Python PIL fallback.

**Lesson Learned:** Always have programmatic fallback for AI-dependent workflows. Rate limits are unpredictable.

#### 3. Sequential Window Execution (W2 → W3 → W4 → W5)

**Explored:** Original plan suggested sequential execution to avoid rate limits.

**Revised:** Actually executed W5 first (dev server), then W3 (grid mockups), then W2 (extraction), then W4 (pending).

**Rationale:** Unblock user feedback early (W5 server + W3 mockups for grid decision), then proceed with extraction.

### Visual and Design Choices Made:

#### 1. Isometric Projection Parameters

**Choice:** True isometric with 60° diamond projection (Option A from Agent B).

**Specifications:**
- Tile width: 64px
- Tile height: 32px (2:1 ratio for isometric)
- Grid origin: Center of viewport
- Coordinate system: Cartesian (x, y) with isometric screen projection

**Impact:** All MAP components must align to isometric grid, buildings/trees positioned with base anchors.

#### 2. Component Thumbnail Size

**Choice:** 150x150px thumbnails for ComponentCatalog.html.

**Rationale:** Large enough to preview details, small enough for grid layout, maintains aspect ratio with white background.

#### 3. Component Naming Convention

**Choice:** `{TYPE}-{NUMBER}` format (MAP-001, UI-001).

**Rationale:** Sortable, clear separation between map assets and UI elements, supports up to 999 components per type.
